MCP 刚发布，我把它当成接口草案

十一月底 MCP 公开。十二月初我读了说明，在本地看了一个最小的工具如何被列出和调用。我没有把它宣布成公司的标准。它太新，我也还没在失败场景里待够。

吸引我的是发现和调用分开。工具有一份自己的描述，宿主按描述去要结果。这比把所有函数说明手写进同一个提示里清楚。清楚是工程上的好事。

草案阶段我最在意的仍是旧问题：调用失败时长什么样，超时谁负责，结果空了能不能被模型当成发挥的许可。协议如果把这些留成各自实现，那它就是接口草案，不是行为契约。草案可以试，契约还要自己补。

我也警惕过早的统一。语音、文本、内部工具的时钟和权限不一样。用一个发现机制把它们登记在一起是可以的，用一套超时和一套权限硬套会把实时链路拖坏。登记不等于同一套运行策略。

十二月的行动很小：本地挂一个只读工具，看日志里能不能区分“没发现”和“发现了但调用失败”。能区分，就值得继续跟。不能区分，就先当文档看。

我不同时改生产路径。生产路径上的函数调用刚把失败形状写清楚，不因为新名字出现就推倒。

新协议的正确欢迎方式是写测试，不是写宣言。测试只覆盖我真正调用的那一个只读工具。

等它过了几次超时和空结果，我再决定要不要在笔记里把“草案”两个字拿掉。

只读工具的日志里我区分了发现失败和调用失败两种行。两种行的文字不同，避免以后用同一个“出错了”概括。概括是草案阶段最容易欠下的债。

只读工具失败时，用户可见的句子只有一句：这次没取到。不解释成长篇原因。长篇原因常常是模型在失败之后开始发挥。发挥要从失败路径里删掉。

一句“没取到”我反复读，确认它没有暗示用户再问就会有。暗示会把失败重新变成闲聊。闲聊不是这条路径的目的。
