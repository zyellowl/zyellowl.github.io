两入口拒绝不一致即分叉

定时去看轨迹，和人在群里问一句，像两个产品。简历里写过大保 CLI 当内核：定时任务通过它跑自迭代，钉钉 Bot 也用它。这里只重复这个选择，不写内部实现。

选择的理由是循环只留一份。同一种编号，同一种空了就停，同一种把权限缩小。入口只负责把一句话或一次定时变成提交。

定时那边容易变成没人看着就可以多试几次。群那边容易变成空了也要多说一句，好让人觉得礼貌。两边一放宽，内核就没了。

我用同一条失败从两个入口各走一次。拒绝的文本和会不会重试得一致。不一致就当成分叉。更讨喜的那一边，我先把它改回短的拒绝，不把短的那边加长。

加长会看起来像解决了，其实是两边一起松。

同一条失败用例我保存了两份日志，文件名分别是定时和群。对比时只看拒绝原文和有没有第二次调用。多出来的客套句算分叉。

两份日志并排放，文件名用入口名，不写通过。通过是我看过之后的判断，不写进文件名。

定时那次和群里那次，我用的是同一条故意写坏的输入：工具返回空。定时日志里是一句“没取到”，没有第二次调用。群的日志里先是这句，后面又跟了一句建议用户换个说法再试。后一句就是分叉。

我把群这边的那句建议删掉，再跑。两边都只剩“没取到”。看起来没那么客气。客气是入口自己加的，不是内核的结果。加回来很容易，因为有人会说群里这样太冷。冷就冷，冷的时候两边还能对上。

重试也试过放宽定时那边。没人看着的时候多试两次，好像合理。两次之后如果第一次其实已经发出去了，只是响应丢了，第二次就是重复动作。所以次数仍放在内核，入口不能单独加大。

简历里写的是大保 CLI 做这个内核，定时任务和钉钉 Bot 都走它。这篇不写命令参数，也不写机器上的路径。那些不该出现在公开笔记里。能公开的就是这个选择：循环一份，入口只提交。

检查方法也不复杂。同一条失败，两个入口，对比拒绝原文和调用次数。多出来的句子算不一致。不一致先改更长的那边。

空结果那条用例是我手写的假工具，固定返回空列表。定时入口打进去，日志一行：没取到。调用次数 1。群入口打进去，同样一行，然后多一句让用户换个说法。调用次数还是 1，但文本长了。长出来的就是入口自己加的。

删掉那句之后我又跑了一次群入口。只剩没取到。我把两次日志并排存在一个目录，文件名用入口名，不写“通过”。通过是我看过并排之后自己的判断，不写进文件名，免得下次没看也以为过了。

定时那边我曾经想把重试改成 3，理由是夜里没人。改完想起响应丢了但动作可能已经发生。3 就变成立刻再做两遍。改回和群一样的次数。次数只在一个地方定义，两个入口都读它。

公开能说的只有这个：大保用一个 CLI 把定时和钉钉接在同一套调用上。命令长什么样、机器在哪，不写在这里。

假工具的代码就十几行，固定返回空列表，并且打印自己被调用的次数。次数打在 stderr，正文日志只留给拒绝句。这样我不会把调试输出当成给用户的话。

群入口多出来的那句，我在代码里搜到是入口拼上去的，不是模型生成的。拼上去的位置有个注释说让回复不要太冷。注释我改成了不要在空结果后面加建议。

定时入口没有这段拼接。所以同一条内核，两边看起来不一样。不一样的来源是入口，我差一点要去改内核。日志并排之后才看出来。

简历里能写的是 CLI 同时给定时和钉钉用。这里能写的也到此为止。参数、机器、群名都不放。
