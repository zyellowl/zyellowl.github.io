Pi 的小内核，并不等于简单循环

Pi 的吸引力不是代码少到可以忽略工程问题，而是它把模型循环保持在一个可读范围，把产品资源、会话、扩展和界面留给外层组合。读它时若只盯着 agent-loop，会错过真正决定行为的边界。

本文依据 badlogic/pi-mono 固定提交 dcd461925db2edf69a43c8135db1180d418afd54 的公开源码。结论区分 production coding-agent 组合路径与可复用 AgentHarness；安全判断只覆盖该快照公开契约，不把 project trust 误写成 sandbox。

不要从最像入口的类开始，要找真实组合根

Pi 仓库分成 model/provider 抽象、通用 Agent、coding-agent 产品层与界面资源。真实生产路径大致从 createAgentSessionRuntime 开始，经 services 工厂进入 createAgentSessionFromServices，再到 SDK 的 createAgentSession，最终创建 Agent 与 AgentSession。Runtime 是 abort、shutdown、dispose 与 recreate 的生命周期拥有者，不是另一个 loop。

Agent 保持模型、消息、工具与队列的较小运行状态；AgentSession 叠加资源加载、事件转发、会话持久化、扩展与产品命令。仓库里的 AgentHarness 适合测试、实验或嵌入，但不能被当作 production composition root。若只从它出发，很容易写出“Pi 的产品就是某个实验 scaffold”的错误结论。

这种拆分让读源码的方法也更清晰：先找谁创建对象、谁注入工具、谁拥有销毁，再进入 loop。对个人 Agent，我希望保留相同原则：核心只认识公共知识查询与受控工具，云服务器的限流、会话隔离、数据 key、进程生命周期在外层 runtime；网页只是 Surface，不直接 new 一个全权 Agent。

生产组合路径把 Agent 与 AgentSession 分开创建，服务、资源加载和生命周期由更外层 runtime 组装。

小 Agent 保存状态，AgentSession 解释产品意图

当用户 prompt 进入时，AgentSession 先处理产品级资源和会话，再把模型状态、消息与工具交给 runAgentLoop。Steering 和 follow-up 不是一个模糊的“追加消息”接口，而是两个队列，对应两个不同的消费时刻。队列存在于 Agent 状态中，外层 session 负责把用户动作映射成正确语义并转发生命周期事件。

这种设计避免 UI 直接修改 messages 数组。若用户在工具运行时追加一句“不要改配置”，系统要知道它是给当前 chain 的 steering，还是等当前 chain 结束后的 follow-up；否则消息插入位置由网络到达时间决定，回放就不可解释。显式队列让输入意图成为协议的一部分，也让测试可以断言它究竟何时被读取。

小内核的前提是外层不偷懒。Abort signal、model 配置、tool registry、session persistence 和扩展资源仍需要明确所有者。把它们都塞回 Agent 会重建一个庞大对象；完全丢给 UI 又会产生隐藏控制面。Pi 的组合层展示了一条中间路线：内核只保留运行必需状态，产品语义在 AgentSession 聚合。

双层循环在明确检查点消费 steering 与 follow-up；正在运行的长工具不会被新 steering 自动抢断。

双层循环的价值，在两个可打断时刻

内层 runLoop 请求模型、处理完整 response、执行这一批 tool calls，再经过 prepareNextTurn 与 shouldStopAfterTurn。之后才会 drain steering，把它放进下一次采样。外层循环在当前 agent chain 停下时检查 follow-up，有内容就再次启动。两类消息都可改变后续工作，但 steering 属于当前链，follow-up 属于下一段链。

必须保留的反例是：steering 不会抢断正在流式生成的 response，也不会取消正在运行的长工具。它的延迟上界包含当前模型响应、整批工具、prepare 与 stop check。用户界面若把“已发送 steering”显示成“当前操作已停止”，就会制造危险错觉；真正的紧急停止必须走 abort/cancel，而不是向队列里塞自然语言。

这个时序虽然不如即时抢断花哨，却更容易维持一致性。工具批次执行到一半时强行插入新指令，旧工具结果是否还进入上下文、未启动调用是否取消、外部副作用是否重试，都需要更复杂的事务语义。Pi 选择在稳定检查点吸收 steering，以较高延迟换较小的状态空间。部署时应把这个权衡明示给用户。

交互含义。Steering 是“下一采样请考虑这句话”，不是急停按钮。要终止长工具，必须使用独立的 abort 路径。

工具有两种顺序：真实完成与模型接收

模型一次可以返回多个 tool calls。允许并行时，实际 body 用 Promise.all 重叠执行，因此 tool_execution_end 生命周期事件可以按真实完成顺序出现：20ms 的工具先于 300ms 的工具结束。最终形成的 ToolResultMessage 则按原 tool-call 顺序 emit 给模型。观察界面可以如实展示速度，模型上下文仍保持稳定配对。

并发策略是 batch 级保守规则：若其中任一工具要求 sequential，整批会串行。若模型因 length stop 导致 tool call 可能被截断，Pi 不冒险执行，而是为所有调用生成失败结果。Terminate 也不是一个工具单方面喊停就成立，批次语义要求最终结果满足对应条件。这里的代码虽短，却包含对不完整参数和混合副作用的明确判断。

把两种顺序混为一谈，会产生两类 bug。若 UI 被迫等原序，用户看不到快工具已经结束；若消息按完成序写回，模型可能将 B 的结果配给 A。正确事件模型应同时记录 call id、source order、startedAt、finishedAt 与 committedAt。这样性能分析和语义回放各取所需，不必让一条时间线承担全部职责。

会话是 append-only 树，但并非每一步立即耐久

SessionManager 以带 id、parentId 和类型的 JSONL entry 保存树。branch(id) 不会改写既有节点的父子关系，它只是把 in-memory leaf 移到旧节点；下一次 append 才以该节点为 parent 形成 sibling。createBranchedSession 则是另一种操作：抽取 root 到目标 leaf 的路径写成新会话文件，并重建相关标签关系。

树结构让探索式 coding 很自然：用户可以回到一个决定前尝试另一条路，旧分支仍是证据。但“append-only”不等于“每个 UI 动作都已落盘”。新 session 在出现第一条 assistant 消息前可能不创建文件，内部 persist 还会延迟 flush。这能避免只输入半句就留下大量空会话，却意味着崩溃窗口必须被测试和说明。

对公开问答，分支树也比覆盖式聊天历史更适合审计：访客的追问可以挂在上一回答下，服务器仍能重建每条路径使用的知识 revision。但隐私边界要更严格——公共与拥有者 session 必须使用不同数据库 audience 和 data key，绝不能因为树结构方便 resume 就允许跨域加载旧节点。

会话文件保存 append-only 节点树；branch 只移动当前 leaf，下一次 append 才形成 sibling，既有 parentId 不会改写。

Compaction 是确定的路径投影，不是模糊截断

构建模型上下文时，Pi 只走当前 leaf 的祖先路径。若路径中存在 compaction entry，buildContextEntries 选择最新一次压缩：使用 compaction 本身、从 firstKeptEntryId 开始的保留 segment，以及压缩之后新增的 entries。更早的摘要不会层层全部塞回模型，路径之外的 sibling 也不会混入当前思考。

完整会话树并未因为投影而删除。getEntries 与树视图仍可看到旧分支和压缩前证据，模型只是拿到预算内的最新工作视图。这与“从数组头部砍到 token 足够”有本质区别：摘要从哪里接管、哪些消息保留、之后发生了什么都有可解释规则。代价仍然存在——摘要内容是有损的，不能替代关键文件和外部回执。

我会把这一点用于个人认知网站的长对话：公开事实来自版本化简历与文章索引，session summary 只保存访客已问过什么、回答走到哪里。即使摘要错误，下一次检索仍可回到事实源。模型上下文是一张临时地图，知识库才是地形；把个人经历只存进摘要，迟早会被压缩成似是而非的故事。

模型上下文采用当前 leaf 路径上的最新 compaction 投影，而完整树和旧分支仍保留在会话证据中。

扩展事务能回滚注册，回滚不了 import 副作用

扩展 loader 采用 pending、commit、discard，先暂存工具、命令和 hook 注册，全部成功后再提交；加载失败时可丢弃框架内记录。这个机制避免半个扩展把 registry 留在不一致状态，是很实用的组合事务。但模块经 jiti import 时执行的顶层代码，以及 extension factory 已做的文件、网络或全局修改，不会随 discard 自动撤销。

Project trust 也只决定是否加载项目级扩展、提示和资源，不是工具逐次审批，更不是 OS sandbox。Pi 的安全文档明确提醒默认没有内建沙箱。把“不信任项目资源”打开并不能限制一个已受信任扩展读用户目录；把 extension transaction 做得漂亮也不能把同进程第三方代码变成隔离插件。安全必须在加载前决定来源，在运行时由容器或系统边界限制能力。

因此公网 Agent 不应加载访客仓库里的扩展，也不应让请求动态选择本机资源目录。可发布工具应静态打包、版本固定、经过权限清单和隐私测试；容器只挂载所需数据，出网按域名白名单控制。Pi 的小内核很适合作为可理解基础，但部署者必须主动补上 sandbox、租户隔离、限流与审计，而不是把这些缺失包装成“自由”。

扩展加载事务能回滚框架注册记录，却无法撤销模块 import 顶层副作用；信任边界必须在加载前建立。

## No Built-in Sandbox

Pi does not include a built-in sandbox. Built-in tools can read files, write files, edit files, and run shell commands with the permissions of the pi process. Extensions are TypeScript modules that run with the same permissions. Package installs, shell commands, language servers, test commands, and other developer tools behave as ordinary local processes.

This is intentional. Pi is designed to operate on local source trees, invoke project toolchains, and integrate with the user's existing development environment. A partial in-process sandbox would be easy to misunderstand as a security boundary while still depending on the host shell, filesystem, package managers, credentials, and extension code. Real isolation needs to come from the operating system or a virtualization/container boundary.

Project trust is only an input-loading guard. It prevents a repository from silently changing pi's settings or extensions before you approve it. It does not make untrusted code, untrusted prompts, or untrusted model output safe. Prompt injection from repository files, comments, documentation, context files, or build output is expected local-agent risk and cannot be reliably prevented by pi.

结论

  • 真实组合根决定资源和生命周期；AgentHarness 只是边界之一，不是产品全貌。
  • Steering 与 follow-up 的差别是消费时刻，steering 也不会抢断当前长工具。
  • 生命周期事件可以按完成序，模型 ToolResult 必须按调用序，两种时间线都应保留。
  • Project trust 与 extension transaction 都不等于 sandbox，公网部署必须自己补齐隔离。

可以复现的检查

快工具先结束，结果仍按原序

两个并行工具以相反顺序完成时，lifecycle events 与写入模型上下文的 ToolResultMessage 是否呈现两种顺序？

  • 让 fake model 同时返回两个调用，第一个延迟 300ms，第二个延迟 20ms，记录事件与最终 messages。
  • 再把任一工具标为 sequential，比较开始时间、总墙钟与输出顺序。
  • 并行时快工具的 tool_execution_end 先出现，但最终 ToolResultMessage 仍按 call 1、call 2 emit。
  • 出现 sequential 工具后整个 batch 串行，事件与消息都反映该保守门控。

实验验证进程内调度顺序，不证明工具触发的外部服务具备幂等或 exactly-once 语义。

Steering 不是工具急停

在一个长工具执行期间排入 steering，新消息会抢断当前调用，还是等完整 batch 和 turn 检查后才进入下一次采样？

  • 启动一个可控制释放的长工具，在 tool_execution_start 后调用 AgentSession.steer。
  • 释放工具并记录 prepareNextTurn、shouldStopAfterTurn、下一次 model call 与 steering message 的先后。
  • 长工具没有因 steering 被 cancel，当前 batch 先产生完整结果。
  • Steering 在稳定检查点被 drain，并只影响下一次 sampling；显式 abort 才能走终止路径。

该结果绑定固定提交；未来若实现抢占式工具调度，必须重新定义半完成副作用与上下文提交规则。
