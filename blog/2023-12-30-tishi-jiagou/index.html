该谈提示架构了

提示工程、SQL生成、LLM应用

营销平台里那个数据分析洞察模块，生成 SQL 一直是我最烦的部分。表多、字段多，Join 一复杂，模型就容易写飞。我后来做的不是再把那句指令润色一遍，而是先用 Schema Linking 把相关表和字段收窄，再用 Dynamic Few-shot 加思维链，把生成依据收敛到当前问题真正用得上的结构和例子。准确率后来从 40% 做到了 92%，中间还把 SQL 的执行反馈接回修正流程。Donato Riccio 这篇把这种多组件的拼法叫做“提示架构”，我读的时候对上了号。

提示工程技术正变得越来越复杂，演变成一些由多个组件构成的复杂系统。对于这样的复杂系统，“提示工程”的定义可能显得有些局限。

这句话我同意。只改一句话的措辞，解决不了“这一轮到底该看哪几张表”。少样本、思维链、字段筛选，已经不是一个文本框里能说清的事。把它们放在一起，更像在搭一套会随问题变化的结构。今年京东云峰会上讲的那个初版 MVP，对外能看起来像“会写 SQL 的对话”，底下其实就是这些部件在协作。

在这篇文章中，我想为与大语言模型交互的多组件系统提出一个更准确的称谓：提示架构。

名字怎么叫并不要紧。我在意的是，他承认这件事已经超出“写一句更好的 Prompt”。角色提示他写了不少，让模型假装成医生、专家之类。这种技巧我试过，短期有时有用，但营销查询里真正把准确率拉起来的，不是给模型一个“数据分析师”的身份，而是别把用不上的表结构交给它，写错了再用执行结果去改。角色可以留，我不会把它当成架构的主梁。

在少样本提示（few-shot prompting）中，我们会在提示语中加入一些期望输出的示例。

示例要有，但不能堆。问题变了，还把上一类查询的例子原封不动塞进去，模型会按错的模式走。Dynamic Few-shot 对我来说，就是先确定这个问题跟哪些表、哪些字段有关，再挑跟它同类的例子。例子是部件，得按问题组装，不是一份写死的说明书。

通过展示理想的推理过程，可以引导模型在面对新问题时模仿这种逻辑思考方式。

思维链在写 SQL 时有用，尤其是多表 Join、字段引用容易绕晕的时候。让模型先说出它打算用哪张表、为什么这样 Join，再落成语句，出了错也比较好查。可推理过程写得再完整，也不等于语句能跑。我们后来把执行反馈接进修正流程，就是因为“想对了”和“跑对了”不是一回事。提示架构如果只停在生成侧，我觉得还少一块。今年这套办法能把准确率拉上来，不表示换一个业务库还能直接套。表结构一变，链接规则和例子都要跟着改，架构得能拆开维护，不能做成一段改不动的长提示词。我也见过一种相反的倾向：什么都拆成组件，主流程反而看不清。我的尺度很实际，一个部件得能单独改、单独验证。Schema Linking 调完，应该能看出送进模型的表是不是对了；思维链调完，应该能看出推理步骤有没有把 Join 说清楚。看不出来的拆，就先不拆。
