编码 Agent 适合改我能读完的 diff

九月我把编码 Agent 的使用写成一条容量限制：一次任务的 diff，必须是我能在一次坐下来读完的。读不完，就不是它的失败，是我把任务开大了。

读完包括注释和它新建的文件。新建文件最容易藏猜测。猜测不在测试路径上，绿灯不会响。三月的清单还在用。

限制带来的后果是任务变碎。碎比大而含糊好。碎的检查点也好写。大任务的检查点往往只有一句“继续”。继续不是状态。

我也拒绝让它同时改接口和改实现。两处一起变，我无法知道行为变化来自哪边。分开两次，中间有一次能运行的提交。提交是给人看的，不是给模型的成就。

这个习惯和实时系统里的小步发布很像。小步不是风格，是回滚单位。回滚单位太大，就等于不能回滚。

九月不评价市场上哪一个编码产品更强。我评价不了。我只能说自己的门槛：读不完就不合并。门槛以上的聪明，我先不要。

团队里如果别人要看我的改动，这个门槛同样保护他们。他们的时间不该花在阅读模型的发挥上。

发挥可以留在草稿分支。草稿分支不进共享历史。

读不完的标准很主观，我就用一个硬界限代替感觉：超过我设的文件数就拆任务。文件数是粗的，但不会在疲劳时放宽。疲劳时放宽的是感觉。

草稿分支我定期删。不删就会有人把它当成几乎能合并的工作。几乎能合并是危险状态。要么读完，要么删掉重来。

文件数超限时，脚本直接拒绝让我看测试结果。先看结果我会找理由保留大 diff。不看结果，就只能拆。拆是这个门槛真正的执行。

我又把当天的输入和输出各存了一份，不把结论写进文件名。文件名只写日期。结论写在正文里。正文可以错，文件还在，就能对照。对照时先看自己有没有把未知说成完成。说成完成的那一句划掉，但不删文件。划掉是为了以后看见自己当时多想结束这件事。输入输出都保留，避免只留下好看的那一稿。
