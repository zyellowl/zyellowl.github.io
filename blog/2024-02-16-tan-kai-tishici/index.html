把提示词摊开看

提示工程、调试、LLM应用

SQL 生成出了问题，我第一件事通常是把这一轮真正送给模型的内容打出来：系统说明、筛过的表和字段、Few-shot 例子、用户原话。不对着这堆东西看，只看框架封装出来的调用结果，很难知道是链接错了表，还是例子带偏了。Hamel Husain 这篇的标题很冲，意思其实就一句：别隔着一层工具猜，把提示词摊开。

通过截获 API 调用，迅速掌握难以解读的大语言模型框架。

他连做法都写得很具体，用代理去截发给模型的请求。我还没有用到 mitmproxy 那种方式，但习惯是一致的：自己拼的上下文，必须能在日志里还原。统一 RAG 平台对外是声明式接口，业务不直接碰向量库，这很好；可一旦问答质量出问题，如果看不到最终进模型的切片和提示，平台就变成了黑盒。封装是给接入用的，排障的时候得能解开。

而仔细研究提示内容正是抵制这种诱惑的有效方法之一。

面对各种封装库，这是我认同的用法。我不完全反对框架，也不想把控制权交出去。LangChain 一类的工具能把流程串起来，省事。可如果提示词是库自动改写、自动补全的，出了错我不知道该改哪一层。营销洞察里，Schema Linking 和 Dynamic Few-shot 是我明确写出来的步骤，出了错可以对着步骤查。框架若把这些藏起来，只留一个“更聪明”的调用，我反而不敢用在要看准确率的任务上。

我对那些使用户与大语言模型之间距离过远的框架持保留态度。

距离过远，就是我改了一处，却看不出模型读到了什么。智能问答那边，SOP 流程是确定的，后来又接了 ChatGLM6B 做自由对话。自由对话更容易让人产生“模型自己会搞定”的错觉。实际上，版本怎么切、当前轮看到哪些槽位和流程说明，仍然得能打开看。对话版本控制做成对在线用户无感知，不等于对开发者也无感知。

通过勇敢地说出“别瞎忙了，直接给我看提示！”来使用这些工具，你实际上是在为自己的选择赋予了更多的主动权。

主动权这个说法我喜欢。工具可以继续用，条件是我随时能看见那一份真正的提示。看见了，才能决定是改例子、改字段范围，还是改检索回来的切片。看不见，就只会换工具、加一层封装，问题还在原处。我现在对新出现的“自动优化提示”的库，都会先问一句：这一轮发出去的原文，我能不能原样拿回来。能拿回来，框架就是工具；拿不回来，我就先不用。
