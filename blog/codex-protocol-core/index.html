一次 Codex 回合，究竟由谁拥有

Codex 最值得研究的不是某个醒目的 while 循环，而是一次工作如何被接纳、暂停、授权、执行、记录和恢复。把这条链走完，会发现它不是让所有东西都经过同一万能对象，而是给不同职责安排了明确边界。

本文只描述 openai/codex 在固定提交 a25e986323931ec54909b0cd936b612f30c8ce46 的公开 Rust 实现。文件身份以提交、路径、symbol 与内容哈希共同固定；正文中的产品判断均标为推论，不把当前界面表现倒推成源码事实。

Submission 不是消息，它先解决任务所有权

观察：公开协议把外部输入表示为 Submission，把核心向外发布的状态表示为 typed Event。但类型本身不是答案，真正的入口链是 CodexThread::submit 进入 SessionIo::submit，由 submission_loop 串行接纳，再交给 turn_input::handle 判断 start 还是 steer。这个顺序说明协议最终要落到一个具体问题：此刻谁拥有正在运行的任务。

若会话空闲，新输入可以创建 RegularTask 并进入 run_turn；若任务仍在运行，输入可能成为 steering，而不是悄悄再起第二个 loop。取消同样必须指向被 session 追踪的任务。于是 TUI、IDE 或 app server 共享的是 Core 的语义边界，不等于它们都直接消费同一个 Rust enum，更不等于界面可以各自复制一份状态机。外层仍可能有协议适配，但任务真相只有一处。

推论：面向面试官的个人 Agent 也不该把每个 WebSocket 当成独立真相。HTTP 请求只提交意图，运行协调器决定新建、续问、拒绝还是取消，并为每次公开运行分配服务器侧 id。这样浏览器断线不会把任务所有权一并带走，重连也不会重复触发副作用。Codex 给出的启发不是照搬命名，而是先让 admission 与 ownership 可回答。

可证伪的问题。同一会话在任务运行中又收到输入时，系统究竟是创建第二个执行者，还是把它交给现有任务？沿 start_or_steer 可以得到源码答案。

StepContext 固定的是一次采样，不是整个世界

观察：StepContext 持有模型与能力信息、推理配置、审批引用、telemetry、环境快照、选中的 capability roots、MCP binding、ToolRouter 与 AGENTS 指令。最关键的效果是：本次请求向模型公布的工具 schema，与随后接受 tool call 的 router/handler 共享同一个 sampling context。模型不会看到 A 版本定义，却在执行时被毫无察觉地送给 B 版本实现。

旧稿把 cwd、sandbox、最终输出 schema 都笼统写成 StepContext 字段，这是不准确的。它们有一部分仍从 Arc<TurnContext> 或 environment 路径进入。准确说法不是“所有权限被冻成一张万能快照”，而是采样所需的能力声明和执行绑定在一个明确边界上，其他长期或回合级状态仍有自己的所有者。这个区别直接决定我们能否正确分析热更新和竞态。

判断：能力快照应尽可能小而完整。太小会产生 schema/handler 的 TOCTOU，太大则让每次请求复制整个世界、阻碍安全更新。个人 Agent 可以固定知识库 revision、允许的检索工具、输出策略版本与模型配置，同时让限流计数和熔断状态保持服务器实时值。把两类状态混成一个快照，反而会让第 20 次限制被旧上下文绕过。

一次 sampling 捕获模型能力、工具路由与关键政策引用，使 advertised schema 和随后 handler 执行来自同一上下文。

模型流中的一个 item，怎样变成可等待的工具 future

一次 response 并非等全部文本和工具都结束才处理。handle_output_item_done 识别完成的输出项：普通 assistant 内容进入历史和事件路径，函数调用则由 ToolRouter::build_tool_call 解析为内部 invocation，并把执行 future 放入 FuturesOrdered。这里先建立调用身份与位置，再允许底层执行重叠；否则两个相同工具的结果只靠完成时间回来，模型将无法知道各自对应哪个 call。

ToolCallRuntime::run 用读写锁表达共享与独占。允许并发的调用取得读侧，非并行调用取得写侧，形成粗粒度 barrier。这能避免一个修改工作区的动作与其他工具随意重叠，但它不是精细的资源锁：两个只触碰不同目录却被标成独占的工具仍会互相等待。并行声明因此属于正确性契约，不应只由性能直觉决定。

结果顺序的所有者也必须说准。Registry 负责查找和分派，不负责恢复原顺序；真正的语义排序来自 turn.rs 的 FuturesOrdered 与 drain_in_flight。工具 B 可以先完成，生命周期日志也可以先看到 B 的物理完成，但交给模型的结果仍等待 A。这样“执行时间”与“对话时间”被明确拆开，可重复性才不会被网络抖动决定。

并行与独占工具通过读写锁形成粗粒度屏障；它约束执行重叠，却不承担语义结果排序。

Router、Runtime、Registry 各管一件事

沿调用链继续走：Router 先判断 payload 属于哪类调用并构造 invocation；Runtime 决定共享或独占执行；dispatch_tool_call_with_invocation 再进入 Registry 查找具体 handler。Registry 还承载 payload 检查、PreToolUse/PostToolUse、telemetry 与生命周期通知。这套分工的价值，是定位故障时能区分“模型叫错名字”“参数不合法”“并发政策不允许”与“handler 自身失败”。

但不能把它宣传成所有工具自动获得完全相同的安全能力。exec、apply_patch 等可沙箱化 runtime 会接入 ToolOrchestrator，MCP 或某些纯 Core runtime 可能有不同路径。PostToolUse 的拒绝还发生在副作用之后，它能阻止结果继续传播，却不能把已经写入的文件恢复。统一 hook 点是一种治理便利，不是事务回滚保证。

这给扩展作者一个严格要求：注册工具时必须同时说明执行模式、审批与隔离路径、失败语义、输出结构和可重试性。仅实现一个 async handler 并不代表它已被治理。代码评审应沿实际调用路径确认工具是否进入需要的 orchestrator，而不是看到 Registry 这个名字就推断 approval、sandbox、timeout 与清洗都已覆盖。

  • Router：把协议 payload 解释为内部调用。
  • Runtime：约束执行是否可以重叠。
  • Registry：解析 handler 并运行通用 hooks。
  • FuturesOrdered：维护返回模型的语义顺序。

Approval 与 sandbox 解决不同问题，却在一次 attempt 里相遇

ToolOrchestrator::run 先计算 approval requirement，再选择 sandbox 和执行 attempt；若受限尝试因为策略允许的原因失败，系统还可能根据拒绝状态与配置进入 escalated retry。Approval 回答“这次意图是否被授权”，sandbox 回答“即使运行，操作系统允许它碰到什么”。两者概念不同，却不是两条永远互不相干的管线，而是在一次执行决策中组合。

审批缓存也不是简单的 command 字符串。工作目录、TTY、sandbox permissions 与环境都会影响一个决定是否可复用。原因很现实：npm test 在只读仓库与带生产凭据的目录里不是同一风险。把批准抽象得太粗，会让一次低风险同意扩散到另一种上下文；完全不缓存则会让用户被重复弹窗训练成无脑点击。

对公开个人 Agent，最安全的交互不是让访客审批服务器动作，而是根本不暴露那些动作。公开模式只挂载只读的简历检索与经过白名单的回答工具，系统层隔离文件和网络，输出端再做隐私边界检查；拥有者模式才进入需要明确授权的能力。低摩擦来自能力裁剪，不来自把 approval 开关默认设为允许。

边界提醒。审批不能替代隔离，隔离也不能替代用户授权；PostToolUse 更不能撤销已经发生的外部副作用。

Durable rollout 与模型看到的历史不是同一份东西

长任务里至少存在两种历史。rollout 需要留下用户输入、模型输出、工具调用、政策决定与压缩 checkpoint，供恢复和审计；模型请求只需要在 token 预算内、结构合法的 projection。若把二者等同，删除旧消息就会破坏证据；若只保存日志却不规范化投影，又会把孤儿 tool output 或缺少 output 的 call 送进 provider。

ContextManager::for_prompt 前的 normalization 承担 call/result invariant：发现 function call 没有结果时补一个 synthetic aborted output，发现没有来源调用的 output 时移除。旧稿把这件事归给 compaction，并描述成寻找“配对安全切点”，同样不准确。Local compaction 的主任务是生成 summary，用选定用户消息与摘要重建 replacement history，同时把来源 checkpoint/window 写入 CompactedItem。

因此摘要不是历史真相，只是下一次推理的工作视图。一次压缩即使模型继续得很顺，也可能遗失命令输出中的数字或失败原因；关键产物必须保存在结构化状态、文件或 durable event 中。对个人 Agent，公开知识库的文档 revision、引用证据和安全判决应在上下文之外保存，摘要只负责延续谈话，不能成为唯一的个人事实数据库。

请求前的历史投影会补齐缺失的调用结果并移除孤儿输出，维护模型上下文中的 call/result 结构约束。

真正值得借走的纪律，以及不该照搬的重量

Codex 的优势来自显式边界：外部表面不必拥有 Core 状态；一次采样的能力声明与执行上下文同源；并发和语义顺序分离；模型投影与 durable rollout 分离。它们让取消、重连、多客户端、工具治理和长任务恢复都拥有具体落点。对一个会长期演进的 coding agent，这些不是抽象洁癖，而是避免第二个入口出现后立即分叉的成本控制。

代价同样可见。typed protocol 要承受版本演进，粗粒度非并行锁会牺牲可安全重叠的吞吐，跨 session、turn、router、runtime 与 handler 的调用链提高阅读成本。Hook 和事件越多，观察者顺序与错误隔离越需要测试。更重要的是，架构不能替代工具本身的幂等性：外部部署在超时后是否已经成功，Core 仍需要领域侧证据。

我的取舍是借三条而非复制整个目录：服务器掌握 run ownership；每次模型请求绑定可重放的知识与能力 revision；每个副作用经过明确的政策/隔离路径并留下结果证据。其余层级等真实需求出现再加。所谓“吸取 Codex 优点”，应该是复现这些不变量和失败实验，而不是把相似的类名搬进一个更小的项目。

结论

  • 先追 Submission 最终交给谁，再谈 Agent loop；任务所有权是取消与重连的前提。
  • StepContext 的价值是同一次采样的 schema/handler 同源，不是冻结所有运行状态。
  • 并发完成与模型结果顺序是两条时间线，排序责任属于 turn 的 future drain。
  • 日志是证据，模型历史是投影；normalization 与 compaction 也不是同一件事。

两个完成时间相反的工具能否并发运行，同时保持下一次模型请求中的 call/result 原始顺序？

  • 在固定提交运行 tool_parallelism 相关测试，令两个工具分别等待约 250ms 并记录开始、完成和提交时间。
  • 把其中一个工具改为 nonparallel，再记录总墙钟时间与其他调用是否越过读写锁 barrier。
  • 并行场景墙钟接近单个慢工具耗时，物理完成顺序可以变化。
  • 下一次模型请求中的工具结果仍按调用顺序排列；nonparallel 场景出现粗粒度屏障。

该实验只证明固定快照中的调度与提交契约，不证明具体工具的外部副作用天然幂等或可撤销。

破坏历史后观察修复

当历史含有缺失 output 的 function call 或没有来源 call 的孤儿 output 时，请求投影会怎样恢复结构？

  • 构造只含 function call 而没有对应 output 的 ContextManager 历史并执行 for_prompt。
  • 再构造只有 output 没有 call 的历史，比较 normalization 前后的 items 与内容。
  • 缺失结果的调用获得 synthetic aborted output，使 provider 不再看到悬空调用。
  • 孤儿 output 被移除；durable rollout 与规范化后的模型 projection 保持可区分。

Normalization 维护结构不变量，却不能恢复真正丢失的工具结果，也不能证明一次外部动作是否已经发生。
