四种 Coding Agent，不能用功能表来比较

四个 Agent 都能读文件、调工具、继续对话，一张勾选表很快就会全是绿色。真正拉开差距的，是输入何时成为任务、工具能力何时固定、副作用前保存了什么、崩溃后系统敢不敢承认未知。

本文的实现结论分别绑定 Codex a25e986、Claude Agent SDK wrapper 542fefb、Pi dcd4619 与 DeepSeek Harness b150a55。Claude 私有 CLI 只比较公开边界；表格不是永恒排名，而是截至 2026-08-26 的架构切片与可复现实验设计。

先固定比较单位：模型表现不是 Harness 表现

同一个 Harness 换模型，任务成功率会变；同一个模型换工具 schema、权限、上下文预算和重试政策，结果同样会变。任何“谁更强”的记录至少应写成：模型 × Harness × 工具/权限配置 × 任务 × 环境 × 预算。缺一项，读者就无法判断提升来自推理能力、提示词、隐藏重试，还是更宽松的权限。

版本也不能只写 GitHub 仓库首页。本文用完整 commit、文件路径、symbol 与 SHA-256 固定证据对象；列表页不拿哈希当视觉主角，文末研究记录才展示它。GitHub 默认分支变化不会改变本文依据，但结论仍有时间边界：新版本可能修掉缺口，也可能重画控制面，届时应新增 revision history 而不是悄悄改成仿佛从未出错。

比较的第一原则因此是可复现，而不是印象统一。Claude 私有核心没有公开源码，就只比较 SDK 公开进程边界；Pi 默认没有 sandbox，就不能假定部署替它提供；DeepSeek Harness 的 preview 语义也不能外推成稳定格式。证据不对称应留在结果里，不能用猜测把四列补得一样漂亮。

四种控制面，解决问题的起点不同

Codex 从 typed Submission/Event 与 session task ownership 出发，把多种产品表面接到共享 Core 语义；Claude Agent SDK 从宿主/CLI 进程边界出发，用 stream-json 同时承载数据与反向控制；Pi 从小型 Agent 状态机与 AgentSession 组合出发；DeepSeek Harness 则从 profile/service composition 与 append-only event log 出发。它们不是同一目录结构的四种写法。

这四个起点分别优化不同演进压力。需要 TUI、IDE、桌面与自动化共享内核时，Codex 的协议投资更有价值；需要从 Python 宿主控制成熟本地 CLI 时，Claude wrapper 的进程和 RPC 契约最直接；需要快速理解、替换 provider 和编写扩展时，Pi 的小内核摩擦更低；需要把事件、持久化、压缩与 bundle 变成可替换服务时，DSH 的组合面最强。

选择不应从 star 数或文件数量开始，而要从失败预算开始：会有几个 Surface、是否多租户、工具会不会产生不可逆副作用、任务要跑多久、是否必须 crash-resume、团队能否维护复杂事件模型。架构优势只有在对应压力存在时才是优势；否则它就是每次改动都要支付的固定成本。

状态的差异，不在“有没有 history”

Codex 明确区分 durable rollout 与请求前 normalized projection；Pi 保存当前 leaf 所在的 append-only session tree，再用 latest compaction 投影；DeepSeek Harness 把 Log 与 Surface 建成一等对象，replacement 仍保留 provenance；Claude wrapper 的 SessionStore mirror 是尽力恢复副本，普通异常有限重试、超时不重试。四者都能“继续聊天”，但证据强度完全不同。

评测不能只验证重启后界面还有文字。应在副作用前后分别 kill 进程，检查已持久化到哪里、模型下一次看到什么、系统如何表达未知。若一个工具已经发送邮件而 result 丢失，最危险的行为是把 absence 当 failure 并自动重试。最可靠的系统也未必知道真相，但会保留幂等键、外部回执或 OUTCOME_UNKNOWN，让下一步不自欺。

这也是个人 Agent 的隐私要求：公共对话、拥有者对话和源码审计文章不能共用一份“万能记忆”。Public session 只持久化脱敏问题与服务器生成 id，知识事实来自发布 manifest；Owner session 有独立数据 key；文章证据只含公开仓库。恢复能力越强，数据分区越要明确，否则所谓长期记忆只是更持久的泄漏。

工具并发至少有三条时间线

第一条是模型声明 call 的 source order，第二条是工具 body 的开始与完成时间，第三条是结果进入模型上下文的 commit order。Codex 用 Runtime gate 加 FuturesOrdered，Pi 允许 lifecycle end 按完成序但 ToolResult 按原序，DeepSeek Harness 用 rolling pool 与 commitReady。实现不同，核心 invariant 相同：物理并发不能破坏 call/result 配对。

只测总耗时会漏掉顺序 bug，只看最终 messages 又看不到 head-of-line blocking。正确 benchmark 应记录每个 call id 的 createdAt、startedAt、finishedAt、committedAt，混合一个慢并行工具、一个快并行工具和一个 exclusive 工具。然后验证 wall-clock、最大并发度、语义顺序与取消传播，而不是只报告“支持 parallel tools”。

工具安全也不能由一个并发布尔值概括。Codex 的非并行锁较粗；Pi 的 batch 内出现 sequential 会整体串行；DSH 未明确 safe 会 fail closed 且未开始调用可 live reclassify。哪种更好取决于工具资源模型和热更新需求。越动态的 registry 越需要记录实际定义 revision，否则一次回放只能知道名字，不能知道当时执行的是哪代实现。

工具 future 可以并发运行，但 FuturesOrdered 与 drain_in_flight 负责按模型调用顺序把结果交回上下文。

权限表面相似，安全承诺却不能横向脑补

Codex 对可沙箱化工具在 orchestrator 中组合 approval、sandbox、attempt 与升级重试，但不是所有工具都走同一路径；Claude wrapper 暴露 permission callback、hooks 与 sandbox 选项，云端隔离仍由宿主负责；Pi 的 project trust 控制资源加载，默认没有内建 sandbox；DSH 的工具政策链可组合，但 SandboxMode 主要描述 file effects。把四列都打一个“有权限”勾，信息反而减少。

更有用的比较是逐层提问：模型是否看得到工具？调用是否需意图授权？执行在哪个 OS/容器边界？网络与凭据是否隔离？副作用后 hook 能否回滚？子代理能否扩大 capability？未知或 policy 服务故障时 fail open 还是 fail closed？每一问都要用实际路径和失败测试回答。

对公开个人 Agent，最强策略是 capability minimization：只暴露简历与已发布项目检索，任何涉及家庭住址、身份证件、私人联系方式、服务器凭据和内部文件的问题都在模型前后双重拒绝；每会话最多 20 次。无需让面试官点击审批，也不需要给模型一个 shell 再祈祷 sandbox 完美。能不装载的能力，比运行时拒绝更可靠。

badlogic/pi-mono，dcd461925db2edf69a43c8135db1180d418afd54，packages/coding-agent/docs/security.md。Project trust，Extensions，Sandboxing

## No Built-in Sandbox

Pi does not include a built-in sandbox. Built-in tools can read files, write files, edit files, and run shell commands with the permissions of the pi process. Extensions are TypeScript modules that run with the same permissions. Package installs, shell commands, language servers, test commands, and other developer tools behave as ordinary local processes.

This is intentional. Pi is designed to operate on local source trees, invoke project toolchains, and integrate with the user's existing development environment. A partial in-process sandbox would be easy to misunderstand as a security boundary while still depending on the host shell, filesystem, package managers, credentials, and extension code. Real isolation needs to come from the operating system or a virtualization/container boundary.

Project trust is only an input-loading guard. It prevents a repository from silently changing pi's settings or extensions before you approve it. It does not make untrusted code, untrusted prompts, or untrusted model output safe. Prompt injection from repository files, comments, documentation, context files, or build output is expected local-agent risk and cannot be reliably prevented by pi.
  • 第 3 行，明确威胁模型。官方安全文档直说 Pi 进程默认继承用户权限，project trust 只控制项目资源加载。
  • 第 5 行，边界。需要真实隔离时必须依赖 OS、容器或虚拟机；信任提示不能替代 sandbox 和逐工具审批。

  const tool = this.resolveExecution(exec.name, exec.agent, exec.parent !== undefined)
  if (!tool?.isConcurrencySafe) return { kind: 'exclusive' }
  try {
    const concurrencySafe: unknown = tool.isConcurrencySafe(exec.arguments)
    return concurrencySafe === true ? { kind: 'parallel' } : { kind: 'exclusive' }
  } catch {
    return { kind: 'exclusive' }
  }

真正的横评要注入故障，而不是问十遍相同 prompt

基础任务可以统一：在临时仓库定位一个有测试的 bug，先只读分析，再请求写入，运行测试并输出证据。随后逐个注入：第二个并行工具先完成、审批服务超时、sandbox 不可用、结果返回前进程崩溃、持久化磁盘满、compaction 期间历史变化、网络响应超时但外部动作已成功。每个故障都对应一个控制面问题。

每个系统至少运行多次 trial，并记录模型与采样配置、Harness commit、工具定义、权限和环境、token/时间预算、人工干预、最终 diff、测试结果与残留副作用。成功不能只看模型最后一句“已完成”，而要由可执行验收决定。一次幸运结果不能说明恢复协议正确；失败后仍留下可解释证据，往往比平均分多两个点更重要。

评测结论也要允许“不适用”和“公开不可知”。Claude 私有 CLI 内部是否采用某种 compaction，不能由 wrapper 实验越权回答；Pi 未提供 sandbox 时，可以在相同外部容器中比较，但必须把容器配置算进 Harness 环境。公平不是抹平差异，而是让每个不可控变量显式进入记录。

这个个人 Agent 的组合取舍

我的选择不是复制任一仓库，而是组合四个已验证的不变量。借 Codex 的 run ownership、request snapshot 与结构化事件；借 Claude wrapper 的双向控制观念，但把宿主隔离当成第一等工作；借 Pi 的小内核、steering/follow-up 语义和可读扩展边界；借 DeepSeek Harness 的 Log/Surface 分离、显式 checkpoint 与 unknown outcome。模型层可以替换，Harness 契约不随营销名变化。

公共 Web 路径会更窄：一份经过人工审阅的简历/项目知识 manifest，受控检索工具，输入主题 guard、输出隐私 guard、按会话 20 次限流、服务器侧运行 id 和 append-only 安全事件。它不会读取任意本机文件、不会执行访客命令、不会把工具 trace 原样发给浏览器。Owner 路径即使未来调用云服务器，也使用独立 audience、凭据注入和网络策略。

评价这套实现也沿同一方法：TDD 先固定隐私、限流、取消、断线重连、输出净化与图文渲染契约；然后用真实浏览器和故障注入验证。所谓吸取四个 coding agent 的优点，不是 README 同时出现四个名字，而是当磁盘满、工具反向完成或访客套取隐私时，系统仍按照公开不变量行动。

结论

  • 横评单位必须包含模型、Harness、工具/权限、任务、环境与预算，不能把模型成绩冒充架构成绩。
  • 功能勾选表看不见 ownership、commit order、durability 和 unknown outcome，故障注入才能看见。
  • 证据不对称要保留：公开 SDK 边界不能被用来补画私有核心。
  • 这个项目选择组合不变量，并把公共能力主动裁窄，而不是复制任一仓库的目录。

可以复现的检查

统一的工具排序试验

在同一模型响应产生慢调用 A、快调用 B 与独占调用 C 时，四种 Harness 怎样区分物理完成、语义提交和 barrier？

  • 固定模型或使用确定性 fake provider，统一三个工具的延迟、返回结构、并发声明与超时。
  • 记录每个 call 的 created、started、finished、committed 时间，以及下一次模型请求中的结果顺序。
  • 所有正确实现都保持 call/result 配对，但并发门、生命周期事件和 head-of-line blocking 不同。
  • 独占工具形成的 barrier 范围可被时间线直接观察，而不是只靠文档描述。

Fake provider 消除了模型随机性，也因此不能评价真实模型是否会根据早到的 UI 事件改变用户体验。

统一的副作用崩溃试验

在外部副作用完成而工具结果尚未可靠提交时，四种 Harness 各自留下什么证据，又如何阻止盲目重试？

  • 工具使用幂等键写入受控测试服务，在服务确认后、Harness 记录结果前强制 kill 进程。
  • 重启并恢复同一 session，检查日志、Surface/messages、状态码、下一步提示与是否重复请求。
  • 结果会暴露各系统的持久化边界；能明确表示 unknown 的实现不会把缺失记录当成确定失败。
  • 外部测试服务的幂等键成为最终真相，Harness 证据决定恢复策略而不是代替业务回执。

需要为每个系统严格固定外部存储和容器配置；否则比较到的可能是部署差异而非 Harness 语义。
