用 SDK 构建智能体

Claude Code、Agent、检索

大保 Bot 是钉钉里的入口，底下跑的是大保 CLI，本机调度 Codex 去查问题、写文档、做总结，再把结果扔回群里。读 Anthropic 把 Claude Code SDK 改名为 Claude Agent SDK 的这篇，我第一反应是：他们说的“给智能体一台电脑”，我们其实已经在这么干了，只不过电脑是同事自己的笔记本，输出在群聊里。

给你的智能体一台电脑，让他们像人类一样工作。

这个原则我赞成。编码 Agent 要是不能看日志、不能进仓库、不能跑命令，就只能根据你粘贴的片段猜。大保 Hub 后来把经过鉴权的日志和调用链交给 Codex、Claude Code，也是为了让它碰得到真实证据。不过“像人类一样工作”不能理解成什么权限都开。保险业务的数据、生产改动，还是得过 CLI 和权限边界。电脑可以给，钥匙不能整串扔过去。

收集上下文 -> 采取行动 -> 验证工作 -> 重复。

这四步写得很干净，我拿大保的自迭代 Loop 一对，发现结构像，手感却不一样。线上 Trace 回流之后，是问题发现、分级修复、沙箱验证、评测门禁、再发布。收集和行动有了，验证也有，可“验证”在我们这儿经常要等评测排期，循环被拉长。没有验证的行动，我不敢让它自动往生产合。文章把验证写进循环本身，这点应该坚持，哪怕因此循环变慢。同事各自贡献 Harness，如果有人把验证理解成“再跑一遍同一条样本”，门禁就失去意义了。我更希望验证对准原始 Trace 的场景，而不是对准一个已经洗干净的例子。

鉴于其局限性，我们建议从智能体搜索开始，只有在你需要更快的结果或更多变化时才添加语义搜索。

我在京东做过统一 RAG 平台，听这句话会下意识反驳：向量检索不是已经很常用了吗。但他们的意思我后来读懂了，是别一上来就上套语义索引，先让 Agent 用搜文件、grep 这类能解释的办法把证据找回来。业务问答里，材料已经在 Workspace 或者知识库里时，声明式检索仍然有用，尤其是要稳、要快的时候。两边不必打架。新做一个内部排查 Agent，我会先给它日志和全文检索，等明确“找不精确、又要变着法问”再加向量。京东那套统一 RAG 不是白做的，声明式检索在材料已经整理好、问题比较稳的时候，仍然更可预期。我只是不再把它当成每种 Agent 的起步动作。

子智能体使用自己隔离的上下文窗口，只将相关信息（而不是它们的全部上下文）发送回协调者。

蚁小保 IM 侧本来就是协调者和领域专家，Graph State 里放计划、槽位、执行状态。专家不必把翻过的全部材料倒回主对话，这个我和他们的看法一致。隔离也有代价，交接时状态会丢。保险对话里退保、理赔常常要带着前面的槽位走，协调者必须把该共享的状态写在 Graph 里，不能指望子 Agent 自己记得。SDK 把这件事说成能力，我更想把它写成纪律：回传只要结论和证据，共享状态放在主状态里，两边都写明。详细材料如果以后还要核对，就放进 Workspace，别寄托在已经结束的子上下文上。
