LLM 系统的几种策略

评测、RAG、LLM应用

年初回看过去几个月做的两件事，一件是营销平台里的 SQL 生成，一件是把文档解析、向量化和检索收成统一 RAG 平台。两边都不只是“会调 API”。Eugene Yan 把 LLM 系统拆成评估、检索增强、微调、缓存、护栏、防御性体验和用户反馈七种策略，我读完没有打算照单全收，但评估和 RAG 两节，几乎就是我正在撞的墙。

评估对团队而言的重要性，是区分迅速推出低质量产品和认真开发高质量产品的团队的关键。

这话听着硬，细想是对的。SQL 生成如果只看几条样例好不好，很容易自我感觉良好。我们后来能把领域内准确率从 40% 做到 92%，靠的是能跑、能对照执行结果，而不是我觉得这句 SQL“看起来像样”。没有评估，改 Prompt、加 Few-shot、换一版模型，都不知道是变好还是变差。

没有评估，我们就像盲人摸象，或者只能靠肉眼检查大语言模型的输出来判断改动的效果。

肉眼检查我做过，也知道它撑不久。查询一类变了，原来眼看能过的例子就不代表性了。执行反馈其实就是一种很窄的评估：语句能不能跑、结果是否对得上预期。它解决不了所有语义问题，但比只盯生成文本要硬。RAG 这边我还没有同等清晰的指标，检索得准不准，常常要靠抽查。平台可以先把入库和检索接口做统一，评估怎么做成日常习惯，我还在找办法。

检索增强生成（RAG）：用于增加最新的外部知识

这个定位我基本同意。模型自己不会带着业务文档来，知识问答要靠检索把材料送进上下文。不过“增加最新知识”说得比较轻。我独立做统一 RAG 平台时，花时间最多的不是选一个更新颖的检索算法，而是把文档、切片、Embedding 和向量集合的关系理清楚，让解析、无感更新和 Embedding 绑定能按同一套流程走。业务侧用声明式 API 接入，不必直接碰 Qdrant 的细节。没有这部分，所谓 RAG 策略落不到可复用的平台上，只能每个项目自己搭一套。

微调（Fine-tuning）：用于提高特定任务的效果

微调被他列为七种策略之一。SQL 这件事上，我还没有走这条路。收窄上下文、补执行修正，已经把准确率拉了上来。不是说微调没价值，是在评估还没完全稳住、检索平台还在收口的时候，先上微调，我分不清到底是哪一层在起作用。缓存、护栏他后面也写了，方向对，只是我这几件事里还没做到那种份上，就不拿没做过的实践去附和。用户反馈这一条，营销工作台倒是有天然来源：语句跑失败、业务说结果不对，都是信号。怎么把这些信号稳定收进来，比再列一条新策略更急。
