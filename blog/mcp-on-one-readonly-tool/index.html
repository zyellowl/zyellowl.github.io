MCP 我开始在一个只读工具上试

十二月我把 MCP 称为草案。二月我给自己加了一个只读工具，用它列一份本地笔记的标题。没有写入，没有网络。范围小，才看得出协议本身帮了什么。

发现和调用的日志现在分得开。这比手写进提示的函数表清楚。清楚我承认。调用失败时的句子，仍是我写的“没取到”，不是协议自带的产品语言。

超时我沿用场景常数，不改用协议示例里的默认感觉。只读工具的超时可以稍长，开口回合里我根本不走这条发现。发现本身也要时间。

空列表回来时，模型仍可能根据标题发挥。协议没有禁止发挥。禁止写在我的校验里：空就停。这条从 2023 年带到现在，换接口不换。

我没有把第二个工具挂上去。第二个工具如果有写入，就要先有调用编号和拒绝路径。编号不是 MCP 的宣传点，是我自己的旧退路。

二月的结论维持草案，但草案已经有一个能跑的只读例子。例子的价值是日志，不是演示视频。

也看到生态里工具描述写得很营销。描述越像广告，模型越容易调用。我把描述写成限制：只返回标题，不返回正文。限制写在描述里，调用才窄。

窄描述不好看。好看的描述会把只读工具说成助手。助手这个词，我这个月还不用。

描述文本我改过三版，每一版都保存调用是否变宽。变宽的那一版用了助手、智能、自动这类词。词一出现，它更常在空列表之后继续说。于是那些词从描述里删掉。

只读例子的日志我给别人看时，先遮住成功的那次，只看失败的两行。别人若觉得失败两行太少，说明他们还在等演示。演示不是我挂这个工具的原因。

三版描述的差异我存在同一目录。目录名按日期。回看时能看见是哪一个形容词让调用变宽。形容词不是实现细节，它会改变模型是否继续说。所以描述也要版本化。

我又把当天的输入和输出各存了一份，不把结论写进文件名。文件名只写日期。结论写在正文里。正文可以错，文件还在，就能对照。对照时先看自己有没有把未知说成完成。说成完成的那一句划掉，但不删文件。划掉是为了以后看见自己当时多想结束这件事。输入输出都保留，避免只留下好看的那一稿。
