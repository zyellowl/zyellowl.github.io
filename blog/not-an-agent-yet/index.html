今年我还不会做 Agent

十一月底我把今年搭过的东西放在一起看：改写提示、向量召回、一条被我拆开的链、函数调用的离线脚本、流式输出的草稿。每一件都能演示。合在一起仍然不是我愿意称为 Agent 的东西。

缺的不是另一个库。缺的是任务边界。什么叫完成，谁来判断完成，失败了停在哪里，能不能重试，重试会不会把已经发生的事做第二遍。我在实时系统里不会漏问这些。面对模型时，我一次次被“它答上来了”带走。

函数调用让我想得太快。模型可以提出调用，不表示系统有权执行，更不表示执行结果会被核对。我的脚本把提出和执行写成了紧挨着的两行。两行之间应该有拒绝、记录和人工看一眼的位置。我为了少写代码把位置省掉了。

检索也一样。召回的原文如果不能被答案逐句指回，答案就仍然是生成。我有过把原文贴在提示里、却允许它综合发挥的版本。综合发挥是聊天的优点，是记录系统的缺陷。

所以今年的诚实说法是：我在学习怎样约束一个会生成的接口，还没有做出一个会负责把任务做完的系统。约束包括材料、格式、延迟和失败。负责任包括停止、核对和留下过程。

十二月我想写的不是下一件新工具，而是把这些约束收成一份自己能看懂的清单。清单比框架短，才有机会在明年还有效。

我把“完成”试着写成一句能检查的话：该调用的已经调用一次，该引用的编号都在候选里，空结果时没有额外猜测。三个条件缺一，任务就还开着。开着就要停在日志里，而不是用一段总结把它合上。

这段定义很窄，窄到覆盖不了真正的业务任务。窄是今年的限度。限度写出来，明年扩展时才知道自己在放宽什么。不写限度，就会把演示说成系统。

三个完成条件写进脚本的退出码。条件不够就非零退出，不打印总结。没有总结，我就不会把半成品贴进周记。
