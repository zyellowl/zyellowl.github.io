事件来源、再跑限制、发出去看什么，有一格空着就先别写闭环

我把这条路拆开：问题从一次留下事件的运行来，修完要在接近当时的限制下再跑，发出去之后还要能看见这类事件。有一截空着，就还是在讨论。

再跑差在哪，得写出来。不写的话，通过的是另一件事。

发布完把单子划掉，新的失败要等有人想起来。我想要的是新的运行自己还能对上旧的事件。

简历里写过大保这条：回流、发现、修复、沙箱、评测、发出去再看。这里不补内部数字，也不把没公开的流程写出来。

试验模板最上面有三个空问题：事件在哪，再跑的限制是什么，发出去看哪一种。有一个空着，标题里就别用闭环、自动完成这种词。

三个空问题印在模板顶部，不能折叠。我试过折叠，结果先写了结论，空问题留到最后空着。顺序一反，循环就被讲完了。

三个空问题放在模板最上面，不折叠。折叠过一次，我先写了结论，问题留到最后还空着。

折叠过一次之后我把模板改成展平的。结论写在空问题前面，那次的笔记我标了作废。
