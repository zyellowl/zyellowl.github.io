DeepSeek Harness：事件日志不是装饰层

DeepSeek Harness 最有意思的地方，不是又发明了一组 Agent 名词，而是把可组合服务、追加事件、模型视图和崩溃恢复接成一套能被故障注入的运行时。它也不是魔法：只要把 append 误写成 fsync，整篇理解就会偏掉。

本文依据 deepseek-ai/deepseek-harness 固定提交 b150a551b8d465e31e418e1b2eaf5e79bbb7d28e（dsh-v0.1.1-rc.2）的公开源码与仓库文档。所有 durability、tool snapshot 与 delegated policy 结论均限定在该 preview 快照。

没有单一 main 值得膜拜，profile 才是产品拓扑

固定快照中的基础 bundle 通过 cordis.patch.yml 逐 row 组装 LLM、Session、JSONL persistence、sandbox、approval、tools、subagent、compaction 与 agent-loop。Web 或 headless profile 再以相同 service id 覆盖配置。模型默认值、telemetry 是否启用、某个 adapter 是否 dormant、shell 在不同平台使用什么 sandbox，都能在组合层看到。

这意味着配置不是代码之外的一层皮，而是依赖图的一部分。只读 TypeScript 类而不读 patch rows，会错过同一个接口在何处被替换、哪些服务根本未装载、默认政策来自哪里。反过来，只看 YAML 也不够：一个 row 决定实现进入系统，具体不变量仍由 service 源码和测试建立。源码审计必须把两层拼回一条运行链。

对个人 Agent，组合拓扑同样应该可审阅：public profile 只装载脱敏知识、只读检索、20 次限流与输出 guard；owner profile 才能装额外工具。两个 profile 即使复用同一 Agent loop，也不能共享数据库 audience、data key 和环境变量。把差异写成显式 bundle，比在 handler 里到处判断 if public 更容易验证。

基础 profile 通过 patch rows 组装 LLM、Session、持久化、工具、沙箱、子代理、压缩与 agent-loop 服务。

Session Log 保存发生过什么，Surface 决定模型看到什么

Session.append 先对 data 做 lossless JSON snapshot 与 deep-freeze，校验 surface intent，分配连续 seq，再同步发布逻辑事件。不是所有事件都成为模型消息：user、assistant、tool result 等 message-producing event 可以进入 Surface，chunk、turn/step boundary 等 log-only event 只留在日志。观察者可以获得细粒度生命周期，模型无需为每个进度 token 付费。

Surface 的 replace 也不是删除旧事件。摘要或其他替换会追加新 message，新的 projection 隐去旧节点，并用 sourceEventSeqs 记录来源。原始 event log 仍能回答“压缩前发生过什么”，deriveMessages 则回答“当前 provider 应看到什么”。这让审计、UI 与模型上下文不再争用同一 messages 数组。

两份历史带来额外责任：任何阅读工具都必须说明自己展示的是 Log 还是 Surface，否则用户会把“模型看不到旧消息”误解成“旧消息已删除”。隐私删除也不能只改 Surface；真正的 data erasure 需要处理持久日志、索引与备份。架构让视图边界清楚，却不会自动完成合规生命周期。

Session.append 同步提交深冻结的逻辑事件并维护连续序号，Surface 只投影能成为模型消息的事件。

最重要的纠正：append 不等于 fsync

Session.append 的同步成功只证明事件进入内存中的逻辑序列并通知观察者。JSONL backend 会把它编码为带校验、可拼接的压缩 frame，并通过 write-behind 窗口批量写文件。进程若在窗口内崩溃，最近逻辑事件未必已经到达稳定存储。因此把 append 称作 durable commit，等于抹掉最需要恢复协议的时间窗。

语义耐久性来自独立 checkpoint policy：在 model adapter 真正接收请求前、顶层工具 body 产生副作用前、下一 step 推导上下文前执行 session/flush。这些位置不是为了让每条 token 都 fsync，而是建立能解释崩溃的边界。恢复时若看到 durable tool/call 却没有 result，系统生成 TOOL_OUTCOME_UNKNOWN，提醒模型不要盲目重试。

这仍然不是 exactly-once。外部工具可能完成副作用后、结果 append 前崩溃，恢复只能诚实标记未知；真正判断要依赖幂等键或外部系统回执。设计的成熟之处不是消灭不确定性，而是把它编码进下一步决策。个人 Agent 若调用云服务器部署，也应记录 deployment id 并查询状态，不能把 HTTP 超时直接解释成失败后重试。

一句话边界。append 是逻辑提交；write-behind 是持久化策略；checkpoint + flush 才建立可推理的崩溃边界。

压缩 JSONL 后端采用带校验 frame 的 write-behind；逻辑 append 本身并不等于文件已经 flush 或 fsync。

## Write path

The plugin copies frozen session events into one controller per live session. The first pending event starts the configured fixed batching window, and later events join without resetting it. Expiry starts one durable append; events admitted during that write form a separately bounded follow-up batch. `session/flush` cancels the wait and drains current and pending batches. A per-session cursor prevents resumed sessions from re-appending stored events, and live sessions are seeded when the plugin loads. The owning backend instance serializes operations for one session; disposal drains every retained controller before teardown. Every logical event remains present: batching only lets one compressed frame or raw fsync carry more records.

一次模型调用冻结得很强，但不要外推到所有工具

Agent 构造请求时先运行 request waterfall，再由 LLM runtime 的 prepare 阶段捕获当前 adapter registration、解析 exact-model defaults、深冻结 config/context，并返回只能 stream 一次的 prepared handle。随后 canonical request header 与 context 被追加到 session。热更新可以影响下一次 call，却不能让本次 capability lookup 与另一代 adapter implementation 拼在一起。

这是一条强而清晰的 model-call boundary：出问题时可以回看当时 provider、模型、默认项、system、tools 与 contextWindow，而不是只看当前配置。但旧稿把同样强度套给工具是错误的。DSH 对工具只冻结参数与部分 finalize 协议，尚未开始的调用会重新分类，body dispatch 仍按当时 registry resolve 实现。

为什么差异合理？模型请求是一次不可分割的远程 stream，跨代拼装几乎无法解释；工具 batch 可能很长，部署希望尚未开始的危险调用及时响应 policy 更新。选择 live reclassification 就必须接受复现复杂度，选择整批冻结则可能延迟安全修复。文章要描述实际边界，而不是为了叙事整齐把两种事务画成一样。

Rolling pool 让 body 并发，commit 仍服从模型顺序

executeToolCalls 在每组开始前重新判断 execution mode；只有 isConcurrencySafe(args) === true 才进入并行，未声明、异常或未知都 fail closed 为 exclusive。Rolling pool 允许安全 body 重叠，工具的 start 与物理完成事件可以交错。并发资格不是永久标签，它可以依赖参数，也会看到尚未开始时的 registry 状态。

结果提交由 commitReady 控制：只有从模型顺序第一个尚未提交 slot 开始的连续 settled 区间才能进入 Log/Surface。调用 c2 可以先完成，却必须等 c1 后才提交 tool/result:c2。这与 Codex、Pi 体现了相同不变量，但实现位置不同；比较 Harness 时应该对齐不变量，而不是只数有没有 parallel 选项。

有序 commit 也会形成 head-of-line blocking：一个很慢的 c1 让后面所有结果等待，即使它们已经完成。换来的好处是 provider 上下文稳定，call/result 不因网络竞速重排。真正优化应从工具分组、超时和可取消性入手，而不是直接让结果抢跑。性能曲线与语义契约必须同时被 benchmark。

rolling pool 允许安全工具重叠执行，但 commitReady 只提交从模型顺序起点连续完成的结果。

工具运行时只有局部快照，政策链也有精确顺序

createExecution 复制并冻结 arguments，并提前捕获定义里的 finalizeContent；dispatchToolBody 却会按当时 registry 重新 resolveExecution。实际链是 pre-execute、approval service、monotonic guards、execute/body、按序 post-execute、已捕获 finalizer、materialize，最后通知 contained observers。把 guard 和 approval 写反，或说“整个工具世界在批次开始时冻结”，都会误导热更新分析。

局部冻结保护的是已经承诺的输入和结果收尾协议，live resolve 让未开始的调用吸收新实现或新分类。代价是同一模型 response 中不同调用可能跨越 registry 更新。审计记录若只保存 tool name 和 args，不保存定义 revision、政策判决与实际 handler generation，就无法完整复现。DSH 在这里提供了可组合机制，但部署者仍要定义所需证据。

Monotonic guard 的含义也应谨慎：后续阶段可以进一步收紧，不能把已拒绝动作重新放开；它不自动让外部副作用可回滚。Observers 应被隔离，避免遥测异常改变业务结果，但若 post hook 拒绝时 body 已执行，系统仍需记录副作用状态。Policy chain 是决策顺序，不是数据库事务。

Compaction 是带 bracket 的 Surface 事务

compactSurfaceRegion 先校验 balanced boundary，再追加 compaction/start 形成可检测的锁。摘要必须比被替换内容更小，成功体依次写 summary 与带 replace intent 的 checkpoint user message，最后追加 end。压缩改变 Surface projection，旧事件仍在 Log；这正是“可继续推理”与“保留证据”分离的具体实现。

稳定性检查也不是全局一刀切。自动 whole-surface compaction 会拒绝任意 Surface 变化；手动 selected-span 只要求所选区间稳定，区间外新增节点明确允许。Log-only event 不一定让摘要过期。若 end append 失败，系统宁可留下 unmatched start，让下一次尝试返回 busy，也不伪装成事务完整。失败是可见状态，而不是被 finally 静默吞掉。

这套设计值得借，但要看见成本：orphan bracket 需要运维修复，summary 服务慢会占用 region，手动与自动模式的并发规则不同。测试不能只有“摘要生成成功”，还要在 summarizer 阻塞时替换 span、让 close append 失败、让摘要不够短。事务的质量由失败路径定义，不由正常截图定义。

压缩用 start/summary/replacement/end 包围 Surface 事务，并在提交前检查目标区间是否仍稳定。

委派权限只能在具体 provider 范围内下结论

基础 bundle 把 spawn 配成 fresh + continuable，把 fork 配成 completed-prefix + one-shot。内置 in-process provider 会把 child approval 固定为 never，并复制父会话显式设置的 sandbox override。若父会话没有 override，child 跟随 deployment default，而不是凭空获得一份冻结的 restricted sandbox。因此“子代理永远不能扩大权限”是超出证据的口号。

结论必须限定：在这个 shipped provider 中，child 不会主动弹出新的审批，并继承明确覆盖的文件效果策略。其他 provider、网络能力、进程策略和部署默认值仍需单独审查。当前 SandboxMode 的词汇主要描述 file effects，也不能据此声称网络已隔离。Preview session format 仍是 v0，同样没有长期迁移承诺。

我的判断是，DeepSeek Harness 最值得吸收的是把恢复歧义、Surface 替换和并发提交写成显式协议；最不该复制的是在未证明部署默认值时使用宏大安全结论。公共个人 Agent 的子任务应继承服务器端不可变 audience 与数据挂载，工具 capability 只减不增，并由集成测试验证，而不是依赖“subagent”这个名字自带最小权限。

内置进程内委派固定 child approval 为 never，只复制父会话的显式 sandbox override，权限结论必须限定在该 provider。

结论

  • 组合 patch 是运行拓扑的一部分，审计时要把配置与 service 源码一起读。
  • Log 保存事实，Surface 是模型投影；替换可隐藏节点，却不等于删除原始数据。
  • Session.append 不是 fsync，副作用前的 checkpoint + flush 才建立可解释恢复边界。
  • 模型调用强冻结、工具局部冻结；热更新语义必须按各自实现描述。

可以复现的检查

反向完成，正向提交

并行工具 c2 先于 c1 完成时，系统能否保留物理完成事实，同时阻止 c2 result 越过 c1 进入 Surface？

  • 让 c1 在可控 barrier 阻塞，c2 立即返回；记录 body completion、event log 与 deriveMessages。
  • 确认 c2 完成后释放 c1，再检查两个 tool/result 的 seq 与 Surface 顺序。
  • c2 body 已完成时，不会出现越过 c1 的 committed result。
  • 释放后 result 按 c1、c2 提交，模型 call/result 配对保持原序。

有序提交会产生 head-of-line blocking；实验不代表所有工具批次都应并行，也不衡量真实网络尾延迟。

副作用后硬崩溃

当 tool/call 已 checkpoint、body 已产生副作用、result 尚未 append 就崩溃时，恢复是否会明确标记结果未知？

  • 在顶层工具 checkpoint 完成后写入外部 marker，并在 result append 前强制终止进程。
  • 重新加载压缩 JSONL frame，检查 durable call、合成结果与下一步模型上下文。
  • 恢复能看到已持久化 tool/call，并生成 TOOL_OUTCOME_UNKNOWN，而不是伪造失败。
  • 提示明确要求不要盲目重试；外部 marker 用于证明副作用可能已经发生。

Unknown 是诚实状态而非自动修复；业务仍需幂等键或外部查询才能决定补偿、接受还是重试。
