Super-agent 设计（二）：套到开放框架上

Super-agent、开放框架、调度中心、agent 插件

系列共三篇：① 逐节读原文 + ELI5 · ② 套到开放框架上 · ③ 开放框架怎么做

上一篇把原文读完了。这一篇把它一块一块对到我们的开放框架上：哪些我们已经想到一起了，哪些是缺口，哪些根本不适用。

先说我们的框架是什么

我们想基于 DSH 做一个保险场景的开放框架。讨论到最后，定位落在一句话上：基于 DSH、懂保险的 agent 调度中心。别的业务用很低的成本接进来，接进来的能力沉淀成我们的领域资产。

中间有一个关键的转折。一开始的想法是“定一套标准，让别人来适配我们、在我们这儿贡献”，后来我觉得这不现实：别人不会为了我们改自己的东西。所以思路反过来，不让别人适配我们，而是我们去接住别人。别的团队已经有自己的 agent，在他们自己的服务上跑，代码、部署、迭代都还是他们负责；我们在 DSH 里挂一个代理插件，里面只放三样：对方的调用地址、自动生成的能力说明、字段映射。DSH 调它就跟调本地插件一样。

可如果只是转发，那就是个网关，别人绕开我们直接调也一样。所以转发上要加四样东西：听懂需求（调用方只说“用户要报案”，由我们判断找哪个 agent）、组合编排（先查保单、再走理赔、最后合规检查）、统一上下文（同一个用户在不同 agent 之间切换，会话和背景不丢）、把关（权限、脱敏、合规红线、链路追踪）。

整个产品拆成六块：

  1. DSH Runtime（内核）：插件加载和生命周期、隔离、权限、链路追踪、超时熔断。这部分不做成插件，否则谁都能替换，整个体系就不可信了。
  2. 调度中心：理解调用方要什么，路由到对应 agent，多个 agent 串起来编排，保持统一会话上下文，做脱敏和合规把关。
  3. 插件体系：统一插件格式和注册中心；插件分能力、知识、守卫、agent（远程或本地）、渠道几类。
  4. 插件生成器：业务方提交现有接口或 agent，coding agent 生成插件，沙箱验证通过后一键上架。
  5. 保险领域层：保单、理赔等领域模型和字段映射，加上条款查询、身份识别等公共服务，随接入越来越多逐步沉淀。
  6. 管理台：观测、评测门槛、调用统计、审批和审计。

工程上基座和应用分仓、各自版本化发布；对用户的 UI 不让 agent 直接吐自由文本，而是吐结构化数据，前端按卡片类型渲染。起点是我们已经在用的 DSH 统一 Runtime：IM、语音和 OpenAI 协议的适配已经收进了同一个协议适配插件里，几个端的会话也已经打通。

我卡住的地方一直是调度中心：它到底该“懂”多少，又该怎么扛住多个 agent 同时在跑。原文的两层架构正好回答了这个问题。

下面一块一块说。

② 调度中心 ↔ Router 层

已经一致的：原文的 Router 只跟人交互、派发任务、跟踪任务之间的关系，不执行任务，甚至不需要 Bash。这跟我们对代理插件的定义是同一件事：对方的 agent 怎么干活我们不管，我们只做登记和转接。“听懂需求”就是 Router 的派单，“统一上下文”就是 Router 作为全局记忆。原文说 Router 的活比想象的简单，轻模型通常够用，这对调度中心的延迟和成本是好消息。

分歧：编排放在哪。我们的调度中心写着“多个 agent 串起来编排”，比如一个报案请求要先查保单、再走理赔、最后合规检查。原文明确说 Router 不拆任务，并且专门对比了 Agent Team：Team Lead 要深入理解任务、规划子任务、频繁协调，推理负担很重，这正是 Router 要避免的。我的结论是：调度中心只做“这个请求属于哪个场景”的派单，固定的串联流程交给一个编排型 agent 插件去做。我们的插件体系里本来就有“agent 插件可以组合其他插件完成一个场景，也能被别的 agent 当插件调用”这一条，原文也说 Worker 内部可以是 subagent 甚至一个 Agent Team，对 Router 透明。这样调度中心保持轻，编排逻辑按场景各自演进。

不适用的：原文用一个常驻 LLM 会话当 Router，靠批处理扛突发流量，压测里到达率从每分钟约 1 条升到约 40 条时，单决策摊销时间从 6.4 秒降到 1.6 秒。那是一个研发团队共用一个实例的场景。我们是面向大量用户的入口，不可能所有用户共用一个会话。原文的取舍在这里依然成立（分得越细，共享的上下文越少），所以我按用户会话分：同一个用户的所有事件落在同一个调度上下文里，对这个人是连续的；用户之间本来就该隔离。

③ agent 插件 ↔ Worker 层

已经一致的：Worker 上下文隔离、一个任务一个；我们的插件“按进程或容器隔离，插件之间调用一律经过 Runtime，不直连”。原文的 Worker 之间也不直接通信，冲突靠共享 Thread 的事件通知自己发现，少数跨任务协调由 Router 转达。

缺口：状态回报协议。原文最硬的一条约束是 Worker 从不直接对人说话，只把状态报给 Router，由 Router 统一回复。对我们来说这不是风格建议，而是接入条件，原因有两个。第一，我们的 UI 是结构化数据加卡片类型，agent 插件回自由文本，前端没法稳定渲染。第二，之前讨论 agent 插件时就意识到它跟工具插件不一样：工具调一次就返回，agent 可能多轮追问、流式输出、长时间运行，中间还可能转人工。这几种情况必须在接口里约定好，用状态而不是文本来表达：进行中、需要用户补充、等人工、完成、失败、这不归我。A2A 的任务状态里刚好有 TASK_STATE_INPUT_REQUIRED、TASK_STATE_AUTH_REQUIRED 这类中断态，可以直接映射。具体结构放在下一篇。

差异：原文的 Worker 是自己的会话，工具齐全、实现透明，能用 prompt 约束。我们的远程 agent 是别的团队的黑盒，约束不了它的 prompt，只能约束契约。所以契约要比原文写得更死。

② 意图路由 ↔ 快慢路径

已经一致的：我在之前做多智能体路由时就是“粗分流 + 槽位校验 + 澄清补齐”，本质上就是先规则后模型。原文把它说得更清楚：高频、明确、稳定的判断写成代码当快路径，大模型当灵活但昂贵的慢路径。保险场景里能在代码里判掉的很多：从哪个渠道进来、调用方是谁、这个用户有没有进行中的案件、是不是点了一个明确的按钮。

缺口一：我们现在是请求驱动。调用方发一个请求，我们路由、返回。但保险的流程天然是长的：报案之后有补材料、审核结果、赔款到账。这些都是外部事件。原文把群消息、CI 结果统统当 Trigger，我们也应该把用户消息、业务方调用、工单状态回调、定时提醒统一成一种 Trigger 进入调度中心，否则统一上下文只覆盖“用户说话”那一半。

缺口二：策略要版本化。原文的语义策略写成 prompt，同时是自然语言扩展点，业务同学想加一条“这类问题先转人工”不用发版。我想照抄，但要加一条：策略有版本，每次路由决定都记下按哪个版本判的、走的快路径还是慢路径。原型仓库里每个 Mandate 都记录 Policy version，就是这个意思。保险要审计，这条省不了。

② 统一上下文 ↔ Thread 订阅

这是缺口里最值钱的一块。用户问了理赔进度，调度中心把它派给理赔的 agent 插件；用户接着说“那我再补一张发票”，这句话不该让调度中心从头再判一次意图，它显然属于刚才那件事。原文的做法是：Router 为某个 Thread 的第一个事件建 Worker，这个 Worker 就订阅这个 Thread，后续事件由代码直通，Router 只看不判。

我们的 Thread 可以是“一个会话里的一个话题”，更好的是用领域对象当 Thread：一个理赔案件、一张保单的一次变更。同一个案件不管用户从 IM、App 还是语音进来，都是同一个 Thread，后续消息直达负责这个案件的 agent 插件。我们几个端的会话已经打通了，再往上加这一层，统一上下文就从“会话不丢”变成“事情不丢”。

原文的实验给了它价值的量级：去掉直通，任务完成时间差不多，但 Router 每轮多做约 30% 的决策，缓存读 token 从 23.2M 涨到 31.8M。调度中心每多判一次就多一次模型调用和一段延迟，直通省下的就是这个。还要照搬两条：超出范围的消息 agent 插件可以交还调度中心重新分派；订阅多对多，一个案件同时关联理赔和合规两个插件时，新事件同时通知两边。

② + ⑤ 统一上下文 ↔ Inline & Spill、Chain of Recall

统一上下文最容易做成的样子，是把用户全部历史塞给每个 agent 插件。原文说放太多会稀释注意力，放太少又会让模型反复调工具。我以前做数据分析工具时吃过类似的亏：完整数据集跟着工具调用一遍遍进上下文，后来只给需要确认执行状态的地方返回状态和条数。这次照原文三步走：先给当前对象的 ID 和摘要；按局部性 inline 相关对象（同一案件最近几条消息、保单关键字段）；超长的截断留指针，agent 插件按需从调度中心的上下文接口取。

Chain of Recall 在我们这儿有现成的骨架：⑤ 保险领域层里的保单号、案件号、被保人本身就是全局 ID，天然能把会话、案件、agent 任务连成引用图。用户隔几天换个渠道问“上次那个事怎么样了”，调度中心顺着用户 → 案件 → 任务一跳跳找回去。这也是领域层除了字段映射之外的第二个用处。

① Runtime ↔ 全双工、存算分离

已经一致的：远程 agent 插件这个形态，本身就是原文第 5 节说的“执行环境不搬”：对方的 agent、数据和凭证留在对方那里，我们只通过接口调。Runtime 的超时熔断也已经在。

缺口：调用 agent 插件要走原文 4.1 的异步模式：调用先返回一个任务 ID（相当于 start()），结果作为新事件回来，调度中心在等待期间照样能接用户的新消息，用户说“算了不办了”就发 stop()。我做实时语音时处理过用户插话打断，那是同一个问题在语音端的样子；现在要在调度中心这一层通用地解决。还要单独盯延迟：插件层层调用，延迟和故障会叠加。我前阵子把语音后端迁到 DSH 统一 Runtime 上，功能对齐后平均还慢大约一秒，那次之后我对“内核里的调用一定要轻”这件事很敏感。

③ 渠道插件 + 卡片 ↔ 多通道

一致。原文说两层架构已经解决了一半：啰嗦的推理和工具调用留在 Worker 里，对外交互归 Router；另一半是按通道定规范，IM 里简短、只在需要决策时打扰（他们验证过每条回复不超过 100 个词），异步通道给结构化、信息密集的内容。我们的做法是 agent 插件回结构化数据，调度中心按渠道插件决定渲染成哪种卡片、详略到什么程度。语音端没有卡片，就由渠道插件把同一份结构化数据转成一句话播报。

⑥ 管理台 ↔ Watchdog

缺口。管理台现在的定义是观测、评测门槛、调用统计、审批和审计，都是“看”。原文提醒了一点：很多异常不是崩溃，进程还活着，但卡在无效循环里或者偏离了目标。远程 agent 也会这样：一直返回进行中、反复要同一个材料、答非所问。所以要有一个独立于调度中心、定时运行的巡检，用模型判断每个任务有没有实质进展，该重试重试、该降级降级、该转人工转人工。我之前参与过 Trace 驱动的自迭代 Loop（定时扫描线上 Trace、规则加模型评测、分级修复、沙箱验证、评测门禁），巡检的骨架可以直接复用那套思路。

护栏 ↔ 安全与隐私

原文把安全放在未解决问题里，我们第一天就得有，好在六块里已经有位置：① Runtime 管权限和数据等级，③ 守卫插件挂在输入输出前后做脱敏、合规和话术红线，② 调度中心把关。我会定三条硬规矩。第一，外部输入（用户消息、工单内容、agent 插件的返回）一律当数据，不能改变权限。第二，凭证不进任何模型上下文，由 Runtime 在调用时注入，这正是原文说的“用凭证但看不见凭证”。第三，路由和调用方身份绑定，身份、租户、目标插件对不上就拒绝。原型仓库有一条设计值得照抄：订阅直通只传上下文、不传授权，一件工作能做到什么程度，在接单那一刻就定死了。

原文没有、我们独有的

④ 插件生成器原文没有对应。它是“低成本接入”能不能成立的关键：业务方给接口文档、代码仓库、MCP 工具或 agent 调用地址，coding agent 生成插件包（能力说明、适配代码、字段映射、测试用例），在隔离沙箱里跑一遍，业务方确认后上架，对方接口变了自动重新生成。原文对它的启发是：生成器产出的不只是“能调通的代码”，还必须产出符合状态回报协议的适配层，否则生成出来的插件进不了两层架构。

⑤ 保险领域层原文也没有，它是通用 agent 系统不会有的东西。上面说了它在 Chain of Recall 里的用处；更根本的是字段映射：对方叫 contract_id 也没关系，接入时映射到我们的保单定义上，映射积累越多，领域资产越厚。

顺序

我们原来定的上线顺序是：先做 Runtime、插件体系、插件生成器，用我们自己现有的插件把流程跑通；再接第一个外部业务，同时把调度中心做起来；领域层和管理台跟着接入的业务慢慢长出来。读完原文，我只想加一个约束：在接第一个外部业务之前，先用一个远程 agent 插件把“调用 → 异步执行 → 状态回报 → 卡片 → 追问直达”整条链路跑通。这条链路上的每个数据结构，就是以后所有插件的契约。具体怎么分阶段、每阶段交付什么、怎么验收，在下一篇。
