编程智能体的六块零件

Harness、编程智能体、上下文工程

同事问我大保到底算不算一个 Agent，我经常答不利索。入口是钉钉 Bot，底下是 CLI，本机再去调 Codex，同事各自塞自己的 Harness。用户看见的是一个会查问题、写文档的助手，我每天改的却是调度、权限、上下文和门禁。Sebastian Raschka 这篇把模型、推理和智能体产品拆开讲，正好用来把自己的工作说清楚。

模型外围的配套系统——比如工具调用、上下文管理和记忆功能——发挥的作用一点都不比模型本身小。

这句话我同意。换模型能涨一点，可大保好不好用，更多取决于它能不能拿到经过鉴权的日志和调用链，Observation 会不会把窗口撑脏，修复之后有没有沙箱和评测接得住。这些都不在模型里。他后面把 Claude Code、Codex 都归成 Coding harness，我看着也像：我们其实是在做一套面向团队排障和治理的 Harness，只不过工作区不是 git 仓库那么干净，更多是 Trace、问题单和各人贡献的 Skill。

大家往往会把“模型本身”、“模型的推理行为”和“智能体产品”混为一谈。

内部讨论里这种混法很常见。有人说换个更会推理的模型，自动修复就能稳；有人把一次回答不好记在“Agent 不行”上。我现在会先问：是模型没推理到，还是工具返回值太吵，还是门禁根本没跑起来。三个问题的改法完全不同。文章把 LLM、推理模型、Agent、Harness 分层，概念上清楚。实际做的时候，这几层会缠在一起。改一个工具描述，既是 Prompt，也是上下文，也是 Harness 的契约。同心圆画着好看，排障还是得顺着一次具体的 Trace 走。

在动手干活之前，编程智能体会先去收集情报（把这些“稳定的事实”打包成一份工作区摘要）。

编码 Agent 的工作区摘要，通常是仓库结构、分支、最近改动。大保这边我对等的东西，是把相关 Trace、权限范围内的日志入口、已知问题说明先收回来，再让 Codex 动手。没有这一步，它只能根据群里那句很短的问题开始猜。摘要会丢细节，这点和后文要说的缓存是一组矛盾：摘要要短才站得住，短了又怕关键字段没了。我还没有一套固定的摘要模板，目前是按任务类型拼，用过一轮觉得丢东西了再补。

一个“聪明”的 Harness，绝对不会在每一轮对话时，都把所有东西揉成一团巨大的提示词重新扔给模型。

这句我当原则收着。稳定的系统说明、工具定义，应该尽量不动；每轮真正变的，是用户新问题、刚返回的 Observation、当前槽位。数据工厂里把“分析用数据”和“只确认跑成功”的返回值分开，也是怕每一轮把整张表再喂一遍。Raschka 从缓存的角度写，我更多是从噪音的角度写，结论接近。他的例子主要停在写代码。生产上还要加上评测门禁、权限边界，以及同事贡献的那些并不整齐的 Harness。零件可以按他的六块来对，装配方式没那么标准。我甚至觉得，对我们来说，评测门禁和权限应该被看成和工具、记忆同一级的零件，少了它们，所谓智能体只是能在内部环境里演示的循环。
