电商 Agent 的取舍

Skills、多智能体、评测

蚁小保 IM 这一侧，一直是协调者加领域专家的路子，LangGraph 做调度，项目评测里路由准确率到过百分之九十。Anthropic 这篇讲电商 Agent，开篇就劝人少用子智能体、多用技能。我读的时候没有马上点头，因为这等于在问：现在这套要不要改。

单一智能体加技能的架构，在质量上始终优于“把所有东西塞进一个提示词”的设计，也优于“子智能体”设计，并且在处理每个任务时，通常成本更低、延迟更小。

标题就写着“优先使用技能，而非子智能体”，后面这句更满。他们的理由我也看懂了：领域很难切干净，退货既要订单又要购物车又要目录，子智能体一切，要么复制权限，要么中途交接。技能则是把说明加载进已经握有完整历史的主智能体。这个判断在“能力模块化、上下文还要连续”时成立。可保险咨询里，退保、理赔、核保的工具、口径和风险并不一样，把它们全堆给一个主模型，上下文一样会脏。我当年把路由做出来，就是不想让一个窗口同时处理所有领域的细节。百分之九十的路由准确率是现成的结果，不是为了架构好看。我会去试：一些轻量、横切的能力改成 Skill 按需加载；真正要隔离工具和口径的专家，暂时不拆。先看 Trace 里交接丢了什么，再决定要不要改主路径。

更糟的是，每次交接都会消耗几倍的 Token，并增加好几秒的延迟。

交接确实贵。专家回传如果把翻过的材料整包送回协调者，Token 和时延会一起涨，状态还可能丢。这点我同意，也已经在往回传结论和证据上收。但“好几秒”放到语音通道里，含义完全不同。语音后端迁到 DSH 之后，功能是齐的，平均还慢大约一秒，我卡在查这段时延。不能因为技能少了一次交接，就假设用户对这一秒不敏感。IM 里多等一会儿，有时能换来更清楚的口径；语音里多一秒，用户已经在等下一句开口。所以我不会把“少用子智能体”单纯理解成省延迟，它更像是在提醒：没有隔离必要的交接，就不要做。

任何与你三分之一及以上流量相关的指令——无论是你在发布前预见到的，还是在生产环境中观察到的——都请放进系统提示词里，剩下的长尾需求则做成技能。

这条经验法则很实用，我也吃过系统提示词越写越长的亏。高频约束、安全底线、不能错的口径，应该常驻。长尾流程放进 Skill，按需出现。问题是“三分之一”在我们这儿不好直接量，流量会按险种和入口变。我更愿意改成：反复在 Trace 里出现的指令，进系统提示词；出现得少、但一旦错了很麻烦的，也先放在常驻约束里，而不是仅仅按调用比例来切。比例是参考，不是门槛。

真正能撬动留存率、参与度和购物车规模等核心指标的，往往是最终结果的质量。

后面那句更刺：相比于挤牙膏般节省出的一点点延迟，答案是否相关、任务是否真正完成，影响要关键得多。质量比乱挤延迟重要，这个大方向我赞成。评测如果只盯时延，很容易把该说清的话砍短。可他们讨论的是电商里“挤牙膏般”的那一点点。语音这边多出来的大约一秒，不是挤牙膏，是用户听得见的停顿。事实率、准确率、时延我们都要，缺哪一项我都不会在评测里放手。现在更别扭的是评测本身偏慢，质量好不好，常常不能很快知道。方法上我认同他们把评估写进发布过程，只是我们还没跑到那个节奏。在那之前，架构上能少做的交接先少做，该隔离的专家先留着，时延该查的继续查。
